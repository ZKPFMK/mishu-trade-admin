# 运营效率一期改造计划与审查

日期：2026-11-03。状态：审查通过，待实施。

## 目标与范围

让操作员从首页找到待办，能检索全部历史工单，在订单、账户、流水、工单和审批间定位对象，并能恢复列表上下文。沿用 MiShu 深浅主题与移动端布局。只查询后台独立数据库，沿用现有业务写接口与权限；不修改来源交易、账本、审批或命令执行规则。

## 初稿 V1

候选范围：运营待办、模糊搜索、工单分页与转交/附件、跨页导航、审计筛选、Worker 健康检查、自动对账、外部告警、权限变更和大规模导入。

## 第一轮审查：业务范围

问题：候选工作跨运营交互、业务流程、基础设施和来源协议，无法用一套验收证明完成；附件还涉及存储、访问控制和保留策略。

修订 V2：本轮仅交付待办、工单完整检索、导航上下文、审计检索。转交、附件、通知、模糊订单搜索、自动对账、监控和导入扩容单列后续项目。现有订单精确检索保留，工单标题支持字面量包含检索。

## 第二轮审查：正确性与授权

发现与修订：

- 待审批必须排除本人申请、过期申请，并匹配角色；模拟申请和真实申请分别按既有有效期处理。没有审批角色时不展示审批待办。
- 我的工单只计算当前应用、本人领取、仍开放的工单；未领取工单与开放对账差异分别统计。未知结果单列，不能表述为执行失败。
- 每项待办必须有可达的筛选列表；来源同步状态继续使用已有上下文栏，不能把 API 健康当作 Worker 健康。
- 全部统计与列表服务端校验应用范围；计数以十进制字符串返回。统计和分页计数/内容分别在一致的只读事务中读取。
- 工单分页不能再有 200 条硬截断；支持有界页码与游标继续查询，稳定排序；游标绑定应用与筛选，不能跨条件复用。旧 `/admin/cases` 默认数组响应保持兼容，新工作列表独立接口。
- 运营处理的工单选择也要检索已领取开放工单，避免新列表完善但申请表仍找不到旧工单。
- 审计增加筛选，不扩大既有可见范围；全局事件仍仅显示当前操作者自己的记录。

## 第三轮审查：实施与回归

发现与修订（V3，最终实施版）：

- 用 hash URL 携带应用、筛选、页码、游标及详情对象；原有 `#trades` 等链接继续可用。各页面保存最近列表地址，支持刷新、浏览器前进后退。切换应用清除该应用的导航上下文，禁止携带另一个应用的游标。
- 对象跳转必须区分订单、账户、流水与工单；非订单流水关联号不强行当成订单。以账户查看流水时由服务端关联分录，而不是把用户输入拼成 SQL。
- 工单详情按编号单独读取，深链接不依赖是否位于当前页；详情刷新和写操作复用原权限检查。
- 不在 URL、日志、截图或提交中保存密码、OTP、token。浏览器验证使用隔离 schema、合成账号和数据，关闭后删除。
- 大页面拆出工作台、工单和路由小模块，避免继续把新功能堆进 `main.tsx`。
- 对真实来源仅增加只读查询；本轮不运行依赖相邻仓库的联调或开启真实命令。

## 实施批次与验收

1. **查询后端**：工作待办、工单工作列表/详情、审计过滤、流水账户过滤、必要索引及 OpenAPI。隔离测试覆盖超过 200 条工单、分页/游标、筛选转义、跨应用、角色/过期排除、未知结果及大整数。通过后本地提交。
2. **运营界面**：首页待办、工单筛选/分页/详情、运营申请的工单查询、审计筛选、URL 状态与对象关联。构建、后端全量回归和隔离浏览器验证通过后本地提交。
3. **最终审查与交付**：检查权限、深链接、前进后退、深浅主题、390px 布局、原有退款/工单/导出流程，修复实际问题。更新操作文档和本计划验收记录，本地提交并重启当前服务，检查健康与首页。

每批提交前执行 `git diff --check`，仅提交源代码与文档；不推送。若审查发现方案需调整，记录原因与最终行为，不能以删掉失败验收代替修复。
