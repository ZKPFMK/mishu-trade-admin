# 真实交易运营处理

本阶段面向现有 **CREDIT 积分交易**实现真实来源操作。交易后台独立运行，仅通过主平台内部 HTTP 接口申请处理；订单、资产归属和账本仍由主平台负责。开启功能不会自动修改历史订单。

## 业务范围

| 操作           | 条件与效果                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------ |
| 未交付托管退款 | 仅 FUNDED，尚无交付或争议记录，托管余额等于订单金额；全部退回买家，保留原流水                    |
| 重试到期结算   | 已交付且原验收期限已到，校验资产归属、托管余额；复用正常结算，按原订单规则分账，不允许缩短验收期 |
| 恢复争议裁决   | 主平台已有经原争议流程验证的 buyer/seller 裁决；只恢复该裁决的执行，后台不能手填裁决结果         |
| 暂停订单       | FUNDED / DELIVERED / DISPUTED；暂停交付、验收、争议执行和超时处理，买卖双方订单页显示暂停状态    |
| 解除暂停       | 必须使用原暂停工单；交付和验收期限延长实际暂停时长，保护用户剩余处理时间                         |
| 积分补偿       | 对用户可用账户记入正数补偿，与平台补偿账户配对记账；同一工单、同一账户只能补偿一次               |
| 补偿冲正       | 必须指定成功的原补偿命令，按完整原金额撤回且只能一次；余额不足时拒绝，不允许任意扣减用户积分     |

已交付或已完成订单不能套用“未交付退款”。实际售后通过工单核验，再决定继续履约或发起平台承担的积分补偿；原成交、分账和资产交付记录不删除、不倒改。已交付数字作品的撤回、部分退款、卖家追偿以及人民币支付、提现需要独立业务规则与支付接入，不在本阶段冒充完成。

## 人员操作

1. 操作员在订单详情点击“运营处理”，或在“异常与审批”点击“发起运营处理”。
2. 选择处理类型，填写处理依据、相关凭证编号和理由，关联本人领取的开放工单；也可直接新建并领取工单。
3. 点击“核对来源状态”，核对真实对象、状态、余额和处理金额。输入当前密码；绑定验证器后同时输入动态验证码或一次性恢复码。
4. 另一名具有同一应用范围的审批员核验处理依据，重新验证自己的身份后审批。申请人不能审批自己的申请。
5. Worker 使用审批绑定的原命令执行。页面自动更新执行结果、来源回执及流水同步状态。工单存在待办申请、未知结果或有效暂停时不能关闭。

申请有效期 24 小时；审批有效期 15 分钟。申请和审批本身不冻结订单。如需要暂停，必须先完成“暂停订单”的独立审批。执行前若用户已完成交付、验收或其他余额变动，原预览失效，系统拒绝旧命令；重新核验后再申请。

权限由角色、应用范围、账号启停、工单负责人、二次身份验证共同约束。口令修改、验证器变更、撤销权限或审批过期会使尚未执行的授权失效；已执行成功的事实仍通过原回执恢复。

## 本地开启

先完成 [主平台历史接入](mishu-local.md)，备份两端数据库，再执行：

```sh
npm run management:enable
# 在主平台仓库执行 npm run local:build && npm run local:restart:server
npm run build
npm run local:restart
npm run management:check
```

配置工具只用于已有本地连接：校验来源身份，备份两端环境文件，配置不同的读写密钥，开启指定应用，并给已有审批账号增加该应用范围。工具不创建测试交易、不操作账本、不重置密码。所有凭据只保存于忽略文件，工具不会打印凭据。

本地账号：`admin@trade-admin.local` 发起，`approver@trade-admin.local` 审批；密码见本机 `.local/credentials.json`。上线必须换成不同实际人员账号，并停用初始化账号。

## 部署配置

主平台：

| 变量                                 | 含义 / 默认值                                                   |
| ------------------------------------ | --------------------------------------------------------------- |
| `TRADE_ADMIN_READ_TOKEN`             | 专用读取密钥，至少 32 字符                                      |
| `TRADE_ADMIN_COMMAND_TOKEN`          | 独立写命令密钥，至少 32 字符，不能等于读取密钥                  |
| `TRADE_ADMIN_APPLICATION_ID`         | 只接受绑定的后台应用编号                                        |
| `TRADE_ADMIN_COMMANDS_ENABLED`       | `1` 启用实际执行；默认关闭                                      |
| `TRADE_ADMIN_REFUND_LIMIT`           | 单笔订单运营金额限额，默认 100000 积分                          |
| `TRADE_ADMIN_ADJUSTMENT_LIMIT`       | 单笔补偿或冲正绝对值限额，默认 1000 积分                        |
| `TRADE_ADMIN_ADJUSTMENT_DAILY_LIMIT` | 来源全局每日补偿与冲正绝对值累计上限，默认 10000，按 UTC 日界线 |

后台：`SOURCE_URL`、`SOURCE_READ_TOKEN`、`SOURCE_COMMAND_TOKEN` 对应来源；`MANAGEMENT_ENABLED=1` 与应用的 `management_enabled=true` 必须同时满足。应用表的 `refund_limit` / `adjustment_limit` 提供第二层限额，取更严格的结果。当前运行时只支持一个真实来源；不要用全局凭据连接多个真实业务来源。

正式部署使用 `NODE_ENV=production`、`COOKIE_SECURE=1`、稳定且独立备份的 64 位十六进制 `TRADE_ENCRYPTION_KEY`。即使进程误设成开发模式，`environment=production` 的应用也强制操作员及审批员完成 MFA。`MANAGEMENT_REQUIRE_MFA=1` 可让测试环境提前强制同一规则。

验证器在“安全验证”中绑定，支持时间型 TOTP。种子加密入库，恢复码只存摘要；验证码防重放，恢复码一次有效。绑定后登录、改密码、资金申请及审批都验证第二因素；绑定会注销其他会话，解绑或改密码注销全部会话。连续二次验证失败 5 次后账号锁定 15 分钟。

正式环境用 `npm run management:check -- --production` 只读检查两端启用状态、独立人员、MFA、初始化账号停用、来源身份和同步、结果未知任务及最近对账。检查失败返回非零状态，适合部署流水线；它不能替代证书、监控、容量和备份恢复验收。内部接口应限制在服务网络；跨主机使用 HTTPS 或受保护的隧道。

## API 契约

后台完整正文 Schema 见 `packages/contracts/openapi.json`。所有 `/admin` 请求继续使用 Session、CSRF、角色及应用范围。

| 后台接口                                              | 用途                                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------ |
| `POST /admin/management/cases`                        | 以核验依据新建并领取工单                                           |
| `POST /admin/management/preview`                      | `{application_id,input}`，读取权威状态和业务指纹                   |
| `POST /admin/management/requests`                     | 固定操作、指纹、理由、依据、幂等键；要求 `password` 和必要的 `otp` |
| `GET /admin/management/requests`                      | `application_id,page,state?`，每页 25 条，前 1000 页直达           |
| `POST /admin/management/requests/:id/approve`         | 独立审批：`reason,password,otp?`                                   |
| `POST /admin/management/requests/:id/reject`          | `reason`，保留被拒申请                                             |
| `POST /admin/management/requests/:id/cancel`          | `reason`，仅申请人且尚未开始派发                                   |
| `/auth/security`、`/auth/mfa/{setup,confirm,disable}` | MFA 状态和绑定管理                                                 |

来源所有路径以 `/internal/trade-admin/management` 开头：

| 路径                        | 凭据       | 内容                                                        |
| --------------------------- | ---------- | ----------------------------------------------------------- |
| `POST /preview`             | 读取密钥   | `ManagementInput`；返回规范化金额、来源 ID、业务指纹和状态  |
| `GET /receipts/:command_id` | 读取密钥   | `{receipt:null}` 表示当前无已提交回执；不能据此另建退款命令 |
| `POST /commands`            | 写命令密钥 | `ManagementCommand`，含固定 intent 与独立 approval          |
| `POST /cancel`              | 写命令密钥 | 同一完整命令，写入永久作废回执，阻止延迟请求随后执行        |

`intent` 绑定命令、应用、来源、操作、金额、业务指纹、理由、依据、申请人和有效期；`authorization` 绑定不同的审批人、审批时限、理由与 intent 摘要。来源重新验证一切业务条件，永远不依赖后台的订单副本计算余额或授权可执行状态。

来源业务版本在订单或账户每次实际更新时递增；即使账户余额变动后又回到原数值，也会让旧预览失效。它与发布读模型的版本不同，不能互换。

## 事务、恢复与停用

资金分录、订单状态、资产归属、变动标记和命令回执在主平台同一数据库事务内提交。命令编号不能重用到不同正文；相同命令重发只返回原回执。与正常交付、验收和超时处理共享来源的事务锁。后台用租约和唯一活动申请约束减少重复处理，最终幂等仍由来源保证。

HTTP 断线或鉴权错误不等于执行失败。后台保留 `execution_unknown` 并持续查询原回执，最长退避 300 秒。发现成功回执后，即使审批后来过期或人员被停用，也照实记录成功。权限失效且来源尚无回执时，用原命令写入作废记录；查询和作废接口在暂停新执行后仍可用。

故障停用：先将主平台 `TRADE_ADMIN_COMMANDS_ENABLED=0`，后台 `MANAGEMENT_ENABLED=0`，重启服务；**保留两端写密钥**以查询/作废在途命令。不要删除未知申请、重新生成命令编号、改写余额或直接回滚一侧数据库。暂停的订单仍保留暂停状态；恢复服务后由原工单处理。

跨系统恢复须先保留原命令与原来源，查询所有在途结果、补齐事件、完成对账。来源财务库丢失后仅靠较旧备份不能证明此前交易未执行，需按备份点和外部业务证据恢复，不可直接重新开放资金操作。

## 验证

```sh
npm test
npm run test:mishu -- /absolute/path/to/mishu-platform
npm run test:management -- /absolute/path/to/mishu-platform
```

使用临时 SQLite 与独立 PostgreSQL Schema，经真实 HTTP 验证双人审批、限额、过期、交付竞争、暂停、补偿冲正、撤权、作废迟到请求、提交后断线回执恢复、浏览器操作和分录守恒。不会对当前本地用户交易执行退款或调账。

TOTP 实现参考 [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238) 并通过其 SHA-1 向量；审批绑定参考 [OWASP 交易授权说明](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)。这些是实现依据，不代表获得安全认证或完成目标环境上线验收。
