# 交易服务工作台设计

日期：2026-10-29。适用仓库：独立的 `mishu-trade-admin`。

## 产品目标

让运营、客服、审核和管理者进入后台后知道需要处理什么，能从一笔交易建立跟进事项，明确负责人和期限，留下调查过程，交给另一人核验，并追踪后续执行。

现有订单副本、账目、数据分析、管理命令、双人审批和审计继续承担原有职责。主平台仍决定订单状态、交付、授权和积分记账。后台通过服务接口协作，不直接打开主平台数据库。

## 岗位与工作结果

| 岗位   | 要回答的问题                             | 第一版入口与结果                                                                 |
| ------ | ---------------------------------------- | -------------------------------------------------------------------------------- |
| 运营   | 哪些交易需要跟进，问题是否已解决？       | 交易跟进：争议、待交付、待验收订单；建立跟进工单；经营分析查看已有成交与退款数据 |
| 客服   | 谁提出了什么问题，谁负责，下一步是什么？ | 客服工单：分类、优先级、负责人、期限、内部记录、等待回应、转交、提交核验、结案   |
| 审核   | 材料是否充分，处理建议有何依据？         | 审核中心：查看提交材料和完整内部记录，核验通过或退回补充；另行处理现有资金审批   |
| 管理者 | 哪些工作积压或超时，团队负荷如何？       | 团队管理：未分派、超时、待核验、各处理人的工作量；分派任务                       |

岗位入口是工作组织方式，权限继续由服务端角色和应用范围决定。运营/客服的处理能力由 operator 承担，核验由 approver 承担，团队管理由 admin 承担，auditor 只读检查，viewer 只读查看。查看某个岗位入口不会获得新的操作权限。系统管理员不会自动获得资金申请或审批权限。

## 信息架构

第一组“日常工作”：我的工作台、交易跟进、客服工单、审核中心、团队管理。

第二组“业务数据”：经营分析、全部订单、生成扣费。

第三组“账务管理”：积分账户、全部流水、分账与版税、对账中心、导出中心。

第四组“系统管理”：应用接入、操作员、操作审计。

默认首页改为“我的工作台”，优先呈现我的待办、未分派、即将/已经超时和待核验事项，再给出相关业务入口。原有经营图表放在“经营分析”，旧链接继续可访问。

## 关键页面

### 我的工作台

- 展示当前应用和同步状态。
- 以数量卡片和真实待办列表呈现工作量，点击进入处理页面。
- 展示本人负责工单、待领取工单、需要核验的事项与交易关注项。
- 没有事项时明确说明当前无待办，并提供查订单/建立工单入口，不填充演示数字。

### 交易跟进

- 从订单当前状态识别需要关注的争议、待交付和待验收事项。
- 正常履约中的订单不直接标成异常。没有来源期限时不推断订单超时。
- 从订单发起跟进时带入订单编号，记录问题、优先级和跟进期限。
- 工单期限是工作人员跟进期限，与主平台交付/验收期限区分。

### 客服工单

工单包含：标题、关联订单、类别、优先级、阶段、负责人、跟进期限、内部处理记录、核验结果、创建和结束时间。

类别：交易跟进、售后、争议、其他。优先级：普通、高、紧急。

流程：待领取 → 处理中 → 等待用户回应或提交核验 → 核验通过/退回补充 → 完成后结案。

等待用户回应仅记录处理阶段，第一版不会代发消息。内部备注明确标注，不冒充买卖双方原始举证。转交、更新期限、核验和结案均记录操作者与依据。

### 审核中心

区分两个环节：

1. 工单核验：检查现有记录和处理依据，另一位审核人员通过或要求补充。通过只代表内部处理建议已核验。
2. 资金操作审批：继续使用现有预览、二次身份验证、独立审批和来源执行。工单核验不能直接触发退款、补偿或改写裁决。

争议工单结案前须完成独立核验。核验人不能是工单负责人或提交人。已存在待执行命令、未知执行结果或有效暂停的工单不得直接关闭。

主动提交核验的普通工单同样需要核验通过才能结案。已通过核验的工单补充材料、调整安排或转交后，原核验失效。存在在途资金申请时冻结人工工单修改，避免审批依据变化；须先取消未执行申请或等待执行结果。需要核验的工单在资金预览、申请、审批和执行阶段都检查核验结果，暂停/解除暂停保留例外以保护履约。已在来源成功执行的结果始终以原回执恢复。

### 团队管理

按当前应用展示处理人的开放工单、超时、待核验和近 7 天结案数量。以实际工单记录统计，历史缺少结束时间的数据不计入近 7 天结案，避免伪造完成时间。等待用户回应可在工单列表按阶段筛选。

管理人员可根据授权分派任务，目标人员必须启用、具有处理权限且被授权当前应用。

## 数据与交互原则

- 保持原有 open/closed 字段兼容，通过新增 stage 表示工作阶段；迁移已有工单。
- 所有新接口检查会话、CSRF、角色与应用范围；关键状态变更使用事务并发保护。
- 不修改账本精度、来源身份、业务版本、回执和双人审批约束。
- 不增加模拟订单或工单来填充本地实际数据。验收使用隔离测试数据。
- 缺少浏览、咨询、访客和复购口径时，不展示虚假的转化漏斗或增长结论。
- 继续支持深浅主题、键盘操作和窄屏布局；长编号和表格不得撑破页面。

## 第一版范围与后续

第一版落地岗位入口、任务优先首页、交易关注列表、可持续跟进的工单、独立内部核验和团队负荷。复用现有订单详情、经营图表、账务和资金审批。

后续单独建设：买卖家自助提交入口、双向站内沟通与通知、受控证据附件、授权/验收约定快照、正式争议裁决与申诉、浏览到成交的行为分析、卖家经营档案。以上依赖主平台的数据与业务规则，不以一个按钮代替真实接入。

## 验收标准

1. 登录默认进入我的工作台，能访问各岗位入口；只读账号看不到可执行的处理按钮。
2. 从订单建立工单，领取、分类、调整优先级/期限、记录处理、转交和等待回应后，刷新仍保留状态。
3. 提交核验后另一名 approver 可通过/退回；本人及越权账号无法核验，争议不能跳过核验结案。
4. 待执行操作与暂停中的工单继续受结案保护，原有退款、补偿、冲正和审批检查保持有效。
5. 不同应用的订单、人员、工单和统计相互隔离，接口拒绝不合法的状态变更。
6. 工作台和团队计数与实际记录一致，已有数据可迁移，空状态、加载和失败均有明确反馈。
7. 构建、隔离接口测试、现有回归通过；浏览器检查工作台、客服流程、审核入口和窄屏布局。
