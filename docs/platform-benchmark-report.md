# MiShu 数据与数字内容交易平台调研报告

调研日期：2026-11-03。对象：数据交易、AI 服务、数据治理、数字商品、电商和支付管理平台。用途：为 MiShu 的岗位工作区、交易处理和后续交易门户提供设计依据。

版本：资料研究版 v1。MiShu 代码审阅基线：`217d97b`。

**交付状态：资料研究与 MiShu 代码差距分析已完成；平台实际操作尚未完成。** 本报告保留 60 个候选平台索引，对其中 23 个代表平台作资料分析，不声称对 60 个平台进行了完整体验。本次没有修改 MiShu 功能、账户、权限或真实业务数据。

阅读顺序：先看第 1 节主要判断、第 5 节现有不足、第 7 节功能优先级；想直接查看参考产品，可从第 8 节的 10 组入口开始。第 3 节提供判断依据，附录 A 保留全部候选。城市数据交易所的深入比较、目标平台形态和分阶段改造建议见[《城市数据交易所深度比较与 MiShu 平台目标形态》](data-exchange-city-comparison.md)。

## 1. 主要判断

MiShu 应优先解决“每个人登录后知道自己要做什么、为什么能做、处理后到了什么状态”，再扩展产品市场和供需门户。功能丰富应表现为任务可以闭环，而非给所有人堆叠相同的菜单和统计卡片。

推荐组合是：参考 AI 平台的成员和资源权限分层，参考数据市场的产品目录与交付授权，参考电商后台的订单和售后组织，参考支付平台的审批、执行状态与对账。没有一个被调研的平台能直接充当 MiShu 的完整模板。

形成六项设计建议，均属于本报告的推导，尚未实施：

1. **统一认证入口，每位工作人员独立账号，按岗位进入工作区。** 五种岗位不等于只能有五个人，也不需要因此建设五套登录服务。多岗位人员可切换工作重点，但切换不能增加授权。
2. **按动作定义权限。** 查看订单、下载报表、发起申请、独立审批、管理人员是不同能力；应用范围与能力同时生效。角色名只是模板，不能充当完整授权规则。
3. **首页围绕待办。** 运营看待处理工单和自己提交的申请，审批人看需要决策的申请，审计看证据和差异，管理员看人员与接入状态，查看岗位看获授权指标与查询。
4. **用一条证据链解释交易。** 在获授权范围内关联订单、积分流水、申请、审批、来源回执、投影同步和对账结果；审批通过不能显示为交易已经完成。
5. **把异常当作正常业务设计。** 未知结果、拒绝、过期、同步延迟、交付失败和权限不足都要有明确原因与下一步，不靠重复提交处理。
6. **买家、卖家和内部工作人员分别建模。** 后续可以买家门户、卖家中心和内部管理台共用身份体系，但各自拥有不同业务边界；当前五种员工岗位不能代替买卖双方的身份模型。

## 2. 方法、证据与未完成项

### 2.1 这次做了什么

- 核查官方权限文档、操作指南、产品页面及公开演示入口，重点比较身份、资源范围、请求处理、交易状态、导出和审计。
- 将候选分成六类，选择与 MiShu 决策直接相关的 23 个平台展开分析，其余保留为候选索引。
- 静态审阅本仓库导航、首页、待办、导出及权限相关代码；没有在本次研究中重新执行五账号运行验收。
- 对结论进行两轮文档自审：先检查事实是否有来源，再检查建议是否适用 MiShu。此处自审不是平台使用测试、外部评审或代码实施验收。

### 2.2 为什么没有实际操作记录

尝试连接浏览器时，工具返回 `The browser access host is unavailable`；随后尝试连接 Chrome 时返回 `Computer Use was not approved to use Google Chrome`。因此本次未进入在线沙盒、未运行互动导览、未登录厂商工作区，也未创建商品、订单、转账或退款。

阅读网页文字、查看演示入口和阅读官方截图说明，均不计为“实际使用”。本报告没有自测截图、点击步数、任务耗时、可用性分数或真实交易结果。浏览器连接恢复且相关访问获准后，可按第 9 节任务书补齐操作证据；企业付费功能还取决于相应试用权限。

### 3.3 城市数据交易所：交易管理平台应如何吸收

本次针对上海、深圳、北京、杭州、广州、贵阳和重庆/西部数据交易中心补充了独立的深度比较报告，见[城市数据交易所深度比较](data-exchange-city-comparison.md)。七个样本的共同业务主线是“主体入场—产品登记—合规/质量评估—挂牌—磋商—合同授权—交付—结算—凭证—争议”，但侧重点不同：上海强调全流程数字化、第三方结算和凭证；深圳强调质量、合规清单、测试样例和交付安全；北京强调权利/用途分置与隐私计算；杭州强调场景化目录、产权登记和数据测试；广州强调场景门槛和监管平台；贵阳强调规则、价格参考和数据商生态；重庆强调行业专区、数字资产和存证。

这组资料把 MiShu 的目标边界进一步收敛为：**先做交易运营内核，再做外部数据市场**。内部后台应围绕主体与产品准入、合规质量、交易合同、交付计量、结算对账、凭证存证、争议异常和规则审计八个工作台组织；买方、卖方、数据商和第三方服务机构应使用独立的外部组织身份。交易对象至少要拆成产品版本、挂牌、场景、授权、交付任务、结算批次和凭证，不能只扩展现有订单表。

城市交易所的“区块链”“隐私计算”“数据资产”等能力不应直接变成 MiShu 首期的可执行按钮。MiShu 先用权威来源事件、不可变审计、对象版本、内容摘要、交付回执和对账结果建立证据链；需要对外验真时，再把摘要锚定到可信存证服务。具体 P0/P1/P2 功能和三阶段改造顺序已写入独立报告。

## 4. 从调研提炼出的完整任务路径

### 4.1 五个岗位的工作入口

以下为建议体验，不是当前页面状态。岗位可以共用获授权的详情组件，但首屏应回答不同问题。

| 岗位       | 首屏要回答的问题                   | 默认内容                                           | 主要动作                                     |
| ---------- | ---------------------------------- | -------------------------------------------------- | -------------------------------------------- |
| 系统管理员 | 谁能访问哪些应用，接入是否正常？   | 人员及范围、应用接入异常、同步信息和配置入口       | 管理授权、定位接入问题；不自动获得资金审批权 |
| 运营处理   | 今天有哪些事需要我处理？           | 我的工单、未领取工单、我的申请、未知结果           | 领取和处理、补证据、发起申请、查询结果       |
| 独立审批   | 哪些申请需要我判断，依据是否充分？ | 排除本人申请的待审批列表、对象和金额、理由、有效期 | 查看证据、批准或拒绝；不代替来源执行         |
| 运营查看   | 授权范围内的业务现在怎样？         | 真实指标、更新时间、查询及保存筛选                 | 查询和获授权的报表工作；导出能力单列         |
| 审计       | 哪笔记录或处理链需要核查？         | 审计检索、对账差异、关联证据                       | 检查和导出获授权证据；不改变业务事实         |

### 4.2 员工处理一笔异常交易

建议路径：运营工作区待办 → 按应用和交易编号定位 → 查看订单、流水和已有申请 → 建工单或补充证据 → 提交处理申请 → 另一审批人独立决策 → 查看来源执行回执 → 等待投影同步 → 核对结果并关闭工单。

每一步应保留对象、处理人、时间、状态和理由。拒绝、过期、执行失败、结果未知和投影未同步都应分别显示；“结果未知”应引导查询权威状态，不能直接显示“再执行一次”。这是设计建议，未在本次实现或运行验证。

### 4.3 后续买家购买一个数字产品

建议路径：搜索/筛选 → 预览和用途说明 → 查看授权、版本、价格及交付条件 → 确认购买 → 获得订单 → 验证付款状态 → 获取交付或使用授权 → 查看更新、失效及售后记录。

应区分产品、订单、付款、授权和交付。付款成功但交付失败不能显示为“全部完成”；撤销授权不等于抹除购买记录。本仓库尚未形成这套完整买家门户，需另立来源契约与业务需求。

### 4.4 后续卖家发布与结算

建议路径：准备产品与版本 → 提交用途、授权和交付材料 → 审核 → 发布 → 接收订单或访问申请 → 履约 → 查看收入、退款调整与结算明细。

发布审核和资金审批承担不同职责。允许修改商品说明，不代表能改已成交订单的授权快照；允许查看收入，也不代表能修改账本或提取资金。

## 附录 B：后续实施前必须确定的问题

1. “运营查看”到底承担看大盘、客服查单还是财务取数？这决定字段和导出能力，不能只看角色名。
2. 管理员是否承担接入故障诊断，最低需要哪些业务上下文？管理授权不应自动变成资金审批授权。
3. 第一阶段仅改内部五岗位后台，还是另有明确买卖双方门户需求？两者的数据实体、身份和验收任务不同。
4. 一个真实员工是否需要在不同应用承担不同岗位？如需要，当前全局角色模型需独立演进。
5. 各产品的授权、版本、交付、退款调整事实由哪个来源服务持有？后台只读模型不能成为第二个事实来源。

以上属于下一阶段需求确认点，本报告已按“先完善内部运营闭环，再扩展交易门户”的假设排序。当前交付停留在研究与建议，尚欠第 9 节的实际平台使用证据。
