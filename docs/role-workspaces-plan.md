# 岗位工作区与读取权限改造计划

日期：2026-11-04。状态：V3 已开始实施；P0 的能力契约、角色工作区、资产目录投影和订单事实分段已落地，仍需继续完成项目授权、组件依赖和真实来源事件接入。依据：[平台调研及当前代码差距](platform-role-research.md)。本计划接续已完成的运营效率一期，不将该期完成状态改写为本轮完成。

## 当前实施记录（2026-11-04）

本轮已经完成并通过隔离 API 与浏览器检查：

- 服务端新增统一能力契约：`business:read`、`operations:read/write`、`approval:decide`、`reconciliation:read/run`、`export:create/read`、`audit:read`、`system:read/manage`。菜单隐藏不再是唯一边界，列表、详情、工作队列、聚合计数、导出、下载、同步和审计接口都会重新校验能力。
- `/auth/me` 返回默认工作区和能力集合；五个单角色账号分别进入系统管理、我的运营、审批工作区、业务概览和审计工作区。统一认证入口保持不变，每个人继续使用独立账号。
- 新增最小应用上下文接口，系统管理员的应用接入详情与其他岗位的业务读取分开；应用选择不会要求非管理员访问接入事件或服务凭证。
- 新增资产目录和资产详情投影，按资产身份汇总标题、版本、许可类型、订单数、已交付数和已完成数，并明确标注这些是订单投影，不是第二本权威订单、所有权或账本。
- 订单详情增加付款/托管、授权摘要、交付、项目使用、退款/分账五段事实视图；项目登记和下载/调用事件没有被伪造为已经存在，等待来源事件契约接入。
- 更新 OpenAPI、角色预览测试和浏览器验收脚本；完整测试、工作台浏览器检查、五岗位浏览器检查和总览浏览器检查均通过。

本记录不表示 P1/P2 已完成，也不表示外部平台实际操作调研已经补齐 H 级证据。

## 目标

使系统管理员、运营处理、独立审批、运营查看、审计五类单角色账号登录后有各自的默认工作区，清楚显示与其工作相关的内容与下一步任务。共用认证、组件和获授权的业务详情。实际员工数量不受五个角色限制，一人一账号；五个体验账号保留，密码不变。

## V1 与第一轮自审：从界面差异转向职责

初稿 V1：给五个角色分别设置首页和导航，复用现有业务页面。

发现：只改标题或隐藏菜单不能解决 API 仍可读取全部内容的问题；把所有角色做成完全隔离的五套系统又会重复实现订单详情。市场供应商、消费者也不等于内部员工岗位。

修订 V2：按岗位组织工作区，共用详情；制定读取、写入、导出和应用范围矩阵。保留统一登录；不建设外部买卖双方门户，不引入厂商套餐/席位模型。

## 第二轮自审：授权与兼容

发现：管理员不能自动获得财务处理/审批能力；详情聚合接口、导出文件及缓存可能绕过菜单限制；旧账号可能有多个角色。当前角色是用户级，不能暗示支持各应用不同岗位。

修订：

- 前后端使用同一份无凭据能力定义，后端按当前会话用户重新校验；不能信任客户端传来的岗位。
- 多角色能力取并集，但业务对象、申请人排除、有效期、双人审批、幂等性和应用范围检查继续成立。换工作区只改变导航重点，不改变有效授权。
- 管理员没有业务读权限时只展示应用接入和系统管理所需信息；拆分应用选择用的最小上下文与管理详情，避免为获取应用名而泄露接入事件/配置。
- 同步约束聚合详情、文件下载、异步任务创建和状态读取。禁止先获取敏感数据再在浏览器隐藏。
- “运营查看”取消批量导出；这是相较当前实现的权限收紧，交付时必须明确说明。其余权限变化也逐项记录，不能借改版增加资金操作能力。

## 第三轮自审：任务落地与验收

发现：只有不同首页仍不能证明员工能完成工作；审批详情需要完整证据；空待办不能用模拟指标掩盖；旧 URL、权限撤销和账号切换可能恢复到其他岗位的页面。

修订形成 V3：以下首页、能力矩阵、实施顺序和验收要求作为实施依据。此处为方案自审，不能代替后续代码审查或运行验收。

## 五岗位默认工作区

| 岗位                | 默认工作区 | 首屏主要内容                                               | 主要下一步                             |
| ------------------- | ---------- | ---------------------------------------------------------- | -------------------------------------- |
| 系统管理员 `admin`  | 系统管理   | 授权范围内人员与权限摘要、应用接入/同步异常、配置入口      | 管理人员、检查接入事件、查看管理审计   |
| 运营处理 `operator` | 我的运营   | 我的开放工单、未领取工单、我提交的申请、未知执行结果       | 领取/处理工单、查询业务、提交处理申请  |
| 独立审批 `approver` | 审批工作区 | 排除本人及失效申请后的待审批列表、申请人、对象、理由与状态 | 查看业务证据、批准或拒绝               |
| 运营查看 `viewer`   | 业务概览   | 交易/积分/分账/生成扣费的只读指标与查询入口                | 按条件查看业务记录                     |
| 审计 `auditor`      | 审计工作区 | 操作审计检索、开放对账差异、业务与审批证据入口             | 检查事件与流水、追踪处理过程、导出证据 |

统计必须来自已有权威查询或本后台只读模型；新增“我的申请”条件必须由后端按当前用户过滤。没有任务时显示真实空状态及原因。同步状态标明数据更新时间与来源环境，不能当作 Worker 存活证明。

## V3 能力矩阵

这是拟实施目标，**不是当前已经实现的权限表**。每项能力仍与应用范围取交集。除人员目录外，下面的业务读取均指授权应用内的记录；本轮不增加“审批员只能读取关联订单”的行级模型，审批证据查询可读取授权应用业务记录。

| 能力                                                   | 管理员 | 运营处理 | 独立审批 | 运营查看 | 审计 |
| ------------------------------------------------------ | ------ | -------- | -------- | -------- | ---- |
| 自己的身份、安全设置、应用最小上下文                   | 是     | 是       | 是       | 是       | 是   |
| 业务概览、订单、积分账户、完整流水、分账、生成扣费读取 | 否     | 是       | 是       | 是       | 是   |
| 工单、申请与执行状态读取                               | 否     | 是       | 是       | 否       | 是   |
| 工单创建、领取和处理，发起运营申请                     | 否     | 是       | 否       | 否       | 否   |
| 审批他人申请                                           | 否     | 否       | 是       | 否       | 否   |
| 对账结果及差异读取                                     | 是     | 是       | 否       | 否       | 是   |
| 发起对账任务                                           | 是     | 是       | 否       | 否       | 否   |
| 导出已获授权业务数据、读取/下载本人导出                | 否     | 是       | 否       | 否       | 是   |
| 人员与应用接入管理、导入、接入事件读取/重试/冲突复核   | 是     | 否       | 否       | 否       | 否   |
| 操作审计读取                                           | 是     | 否       | 否       | 否       | 是   |

说明：

- 管理员仍可按既有规则管理授权应用内人员；未获业务读取角色时，不出现订单、积分或财务导出。原有管理员兼运营等多角色账号按并集保留功能。
- 接入事件重试、冲突复核、导入从当前部分 `operator/admin` 能力收敛至管理员；不属于资金来源写命令。对账差异领取/复核沿用运营职责，审计只读。
- 审计可检索审批及工单证据，但不能领取、关闭、批准、拒绝或发起对账。导出仍仅限本人任务和当前授权数据，不新增查看他人导出能力。
- 每条修改路由沿用原有审计、CSRF/MFA、对象状态检查。真实来源命令开关、独立凭据和来源事务验证继续由原服务控制。
- 管理员授权变更流程的重新设计、每应用不同角色、行/字段级脱敏和自定义角色另立需求，本轮不宣称实现。现有授权管理不得通过本次首页重构新增绕过路径。

## 导航、路由与响应规则

1. 空入口按角色默认工作区进入。多角色默认优先级为管理员、运营、审批、审计、查看；同时显示已有岗位入口，审批待办在有审批角色时可达。
2. 显式合法业务深链接继续有效。不合法/无权路径规范化到获授权工作区并说明无访问权限；未授权组件不挂载、不发送其数据请求。
3. URL 中的角色或应用参数不构成授权。未知角色不继承只读权限；没有可用应用或能力时显示无授权状态，不静默获取默认应用数据。
4. 导航记忆以用户与应用隔离；退出、会话失效和身份变化清除前一身份的页面数据与导航。相同用户的有效深链接可保留，切换应用不沿用旧游标与对象。
5. 账号在另一会话被停用或撤销角色/应用后，后续 API 请求按最新授权拒绝；前端收到拒绝后刷新身份及菜单，清除失权内容。
6. 数据 API、统计卡片、详情中的关联内容、分页总数和后台任务遵守相同规则。没有权限的卡片不请求、不显示，不返回伪造的 0。
7. 获授权页面间的关联链接保留筛选上下文；目标能力不存在时不显示可点击入口。服务端读取聚合详情时明确省略未授权的附属字段，独立请求未授权资源返回 403。

## 实施顺序与提交

### 批次一：授权契约与后端

- 清点 `app.ts`、`management.ts` 及所有列表、详情、统计、异步任务、文件接口，形成路由与能力对应表，覆盖旧兼容接口。
- 增加共享能力定义；应用最小上下文与接入详情分开；根据矩阵调整读取/写入入口。保留 API 兼容字段时，不向无权人员暴露敏感数据。
- 待办按能力返回；新增本人申请条件、管理摘要所需查询时仍受应用与用户隔离。计数和金额保持精度，游标继续绑定用户、应用与筛选。
- 完成隔离测试及 `git diff --check` 后本地提交，记录哈希。不推送。

### 批次二：五岗位工作区

- 抽出岗位导航与工作区模块；共用业务详情与现有主题。按上述五种首屏内容实现任务入口，不能只换标题。
- 运营默认我的工单；审批默认待我审批；审计默认审计检索及差异；管理员默认系统管理；查看默认业务概览。
- 修正无权路由、导航用户隔离、退出/失效缓存、应用切换及关联链接。所有页面继续显示真实身份与应用/环境。
- 构建及隔离浏览器验证通过后本地提交，记录哈希。不推送。

### 批次三：回归、文档与本地运行

- 更新五账号体验指南和验收记录，列出权限收紧及旧链接的处理方式。
- 跑必要后端与浏览器回归，检查深浅主题和 390px 布局。只在隔离环境验证资金相关模拟流程。
- 重启本地 API/Worker，使用现有五个体验账号验证真实本地入口与首屏，无需重建账号或改密码。
- 提交验收文档并报告全部本地提交哈希；不推送，不启用真实命令。
